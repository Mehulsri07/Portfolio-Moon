134 MB to 6.4 MB: moving StrataField from Electron to Tauri

What made the old installer so big, what moved into Rust, and how existing data came along without being touched.

Why the Electron build was 134 MB

The first version of StrataField was an Electron app. Electron bundles its own copy of Chromium and Node.js into every app, so even a small record keeper shipped a full browser. The installer came to 134 MB for what is mostly forms, a map and drawings.

What Tauri changes

Tauri 2 draws the interface in WebView2, the browser engine that Windows 10 and 11 already include, and pairs it with a small Rust program. The screens are still React and TypeScript; what changed is everything that touches the computer itself.

The installer is 6.4 MB, and that includes the full user manual as a PDF.

What moved into Rust

I kept the Rust side deliberately thin. It owns a fixed set of commands the screens may call (save a borewell, add a photo, make a backup) and the database layer underneath them. Validation, the Excel reader, the water-depth estimates and the cross-section geometry stayed in TypeScript in a shared core package, where they're quicker to change and are covered by unit tests.

Replacing sql.js with native SQLite

The Electron version stored everything with sql.js, which is SQLite compiled to WebAssembly: the database lives in memory and is written back to disk as one file. Moving to native SQLite through Rust meant real transactions, and a schema that can change safely:

  • The schema carries a version number, and an older database is backed up and then upgraded one step at a time.
  • A database from a newer version of the app is refused and left alone, so an old copy can never damage newer data.
  • Every change is written to the record's history, and deleted borewells go to a Recycle bin first.

Bringing existing data across

People already had records in the Electron app, so the first start of 1.0 looks for the old database and imports it automatically. The old file is only ever read, never changed, so if anything went wrong the original data would still be there. The end-to-end test covers this path: it starts the real app with a made-up copy of the old data and checks it all arrives.

What I'd tell myself at the start

  • Keep the native layer boring. The less logic in Rust, the less there is to rebuild when the UI changes.
  • Treat migration as a feature with tests, not a script you run once.
